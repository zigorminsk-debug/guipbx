# FlowPBX — визуальный конструктор маршрутов Asterisk

[![CI](https://github.com/zigorminsk-debug/guipbx/actions/workflows/ci.yml/badge.svg)](https://github.com/zigorminsk-debug/guipbx/actions/workflows/ci.yml)
[![Release](https://github.com/zigorminsk-debug/guipbx/actions/workflows/release.yml/badge.svg)](https://github.com/zigorminsk-debug/guipbx/actions/workflows/release.yml)
[![GitHub Pages](https://img.shields.io/badge/демо-github.io-0b8c70)](https://zigorminsk-debug.github.io/guipbx/)

Интерактивный UI-прототип на русском языке. Главный файл — `index.html`: откройте его в браузере; сервер, сборка и внешние библиотеки не требуются. Прототип хранит рабочие схемы в `localStorage` браузера.

## Что уже можно делать

- Переключаться между тремя примерами: **входящий маршрут**, **исходящий маршрут**, **переадресация**.
- Добавлять блоки кликом из библиотеки или перетаскиванием на рабочее поле.
- Перемещать блоки за шапку карточки.
- Строить ветви: клик по выходному порту → клик по входу другого блока.
- Редактировать свойства, выбирать связи в инспекторе, дублировать и удалять блоки/связи.
- Отменять и повторять изменения; схема автоматически сохраняется локально в браузере.
- Проверять обязательные связи, пробовать симуляцию выбранного пути и смотреть пример `extensions.conf`.

## Важное ограничение

Это **кликабельный прототип интерфейса**, а не подключённая АТС. Симуляция подсвечивает путь на схеме и не создаёт реальный звонок. «Опубликовать» намеренно не применяет настройки. Экспорт `extensions.conf` — демонстрационный пример: перед использованием надо сверить контексты, шаблоны набора, `PJSIP`-эндпоинты, очереди, имена аудиофайлов, таймауты и поведение конкретной версии Asterisk.

## Что взято из Oktell

В редакторе Oktell документация описывает три ключевые области: визуальное поле сценария, окно компонентов и инспектор свойств. Объекты располагаются на поле и соединяются стрелками; у объектов меняются свойства. Эта модель использована здесь как ориентир, а не как копирование интерфейса: [документация редактора сценариев Oktell](https://wiki.oktellstudio.ru/Редактор_сценариев).

## Техническая основа Asterisk и рекомендуемая реализация

У Asterisk есть два подходящих пути исполнения графа:

1. **Компиляция графа в dialplan.** Схема сохраняется как JSON (`nodes`, `edges`, типы блоков, свойства и координаты), сервер валидирует её и генерирует контексты в `extensions.conf`. После pre-flight проверки опубликованную конфигурацию можно загружать через `dialplan reload`. Это естественный вариант для типовых IVR, расписаний, очередей, набора и переадресаций. Официальная документация называет dialplan языком описания обработки звонков; файл конфигурации обычно `extensions.conf`: [Asterisk dialplan](https://docs.asterisk.org/Configuration/Dialplan/).
2. **Динамический runtime через ARI.** Входящий вызов направляется из dialplan в `Stasis(app, flowId, version)`. Сервер FlowPBX принимает события ARI по WebSocket, интерпретирует активную версию графа и управляет каналами/медиа через ARI REST API. Официальная документация описывает связку REST API + WebSocket-события + `Stasis()` как основу приложений управления коммуникациями: [ARI overview](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/) и [Getting Started with ARI](https://docs.asterisk.org/Configuration/Interfaces/Asterisk-REST-Interface-ARI/Getting-Started-with-ARI/).

**Практическая рекомендация:** для первой production-версии начать с compiler-подхода и ограниченного каталога проверенных блоков; ARI добавить для более динамичных сценариев и наблюдения за активными каналами. Пароли ARI/AMI и доступ к CLI должны храниться только на сервере — никогда в браузере.

### Компоненты production-MVP

- Web UI и версионируемая схема JSON.
- Backend API с ролями и аудитом изменений.
- Валидатор графа: один вход, корректные порты, отсутствие необработанных ветвей и циклов, допустимые назначения и ограничения набора.
- Dialplan compiler для разрешённого набора узлов.
- Отдельный deploy-agent рядом с Asterisk: резервная копия, проверка конфигурации, атомарная публикация, `dialplan reload`, проверка результата и rollback.
- Интеграционный тестовый контур с отдельной тестовой АТС; симуляция схемы в UI не заменяет SIP-тест.

Перед включением исходящих маршрутов нужны allowlist направлений/транков, лимиты, защита от toll fraud, журнал публикаций и контроль Caller ID. Доступ к ARI/AMI следует ограничить сетью и защищать аутентификацией/TLS.

## Локальная работа

Нужен только Node.js 20.11+ (браузер для тестов не скачивается — смоук-тест работает на jsdom).

```bash
npm install      # зависимости проверок (html-validate, jsdom)
npm run serve    # локальный просмотр: http://localhost:8080
npm run verify   # полный цикл: линт → сборка → линт dist → смоук-тест
```

| Команда | Что делает |
| --- | --- |
| `npm run lint` | проверка разметки `index.html` (пресет `html-validate:document`) |
| `npm run build` | собирает `dist/`: страница с метаданными сборки, `manifest.json`, копии `.gz` и `.br` |
| `npm run lint:dist` | проверка собранной страницы |
| `npm test` | смоук-тест: запуск страницы в jsdom и ключевые сценарии (старт, вкладки маршрутов, инспектор, поиск по библиотеке, зум, экспорт `extensions.conf`, валидация, добавление блока, undo, автосохранение в `localStorage`) |
| `npm run test:src` | тот же смоук-тест, но по исходному `index.html` |
| `npm run serve` | статический сервер (`dist/`, если собран, иначе корень) |
| `npm run clean` | удаляет `dist/` |

Страница остаётся самодостаточной: сборка падает, если в `index.html` появятся внешние
или абсолютные (`/…`) ссылки на ресурсы, синтаксическая ошибка во встроенном JS,
несбалансированный CSS или пропадёт id, который код читает при старте.

## Автосборка в GitHub Actions

| Workflow | Триггер | Шаги |
| --- | --- | --- |
| [`.github/workflows/ci.yml`](.github/workflows/ci.yml) | push в `main`, pull request в `main`, ручной запуск | `npm ci` → линт → сборка → линт `dist/` → смоук-тест → артефакт `flowpbx-dist` → публикация на GitHub Pages (только для `main`) |
| [`.github/workflows/release.yml`](.github/workflows/release.yml) | push тега `v*`, ручной запуск | проверки и сборка → GitHub Release с файлами `flowpbx-<tag>.html` и `flowpbx-<tag>-dist.zip` |

Демонстрация после публикации: <https://zigorminsk-debug.github.io/guipbx/> (источник Pages — «GitHub Actions»).

Новый релиз:

```bash
npm version patch --no-git-tag-version   # поднять версию в package.json
git commit -am "chore: release v0.2.0"
git tag v0.2.0 && git push origin main --tags
```

## Структура репозитория

```text
index.html              приложение целиком: разметка, стили и логика
scripts/build.mjs       проверки целостности и сборка dist/
scripts/smoke.test.mjs  смоук-тест интерфейса (node:test + jsdom)
scripts/serve.mjs       локальный статический сервер
.github/workflows/      ci.yml и release.yml
dist/                   результат сборки (в git не попадает)
```
